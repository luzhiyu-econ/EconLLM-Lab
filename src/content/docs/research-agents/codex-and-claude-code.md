## 一、网页与 API：两种使用入口

在介绍 Claude Code 之前，先区分两种常见的大语言模型使用方式：直接打开网页与模型对话，或者通过 API，将模型接入自己编写的程序。理解两者的区别，需要先看模型实际接收了什么。

我们在对话框里输入的一句话，只是输入的一部分。应用还可能向模型提供任务规则、历史对话、参考材料，以及工具执行后返回的信息。这些内容共同构成模型当前可用的上下文。模型本身的参数则来自训练，普通的提示词调用通常不会修改这些参数。

在常见的 API 设计中，系统指令或开发者指令用于规定应用中的任务要求，例如怎样处理输入、采用什么输出格式；用户消息提供当前问题和材料；历史消息保留此前的交互。开发者可以分别组织这些内容，而不必把全部要求拼成对话框里的一段话。[OpenAI 官方文档：消息角色与指令](https://developers.openai.com/api/docs/guides/prompt-engineering)

例如，我们希望搭建一个信息提取程序，可以把“按照给定字段提取内容，以 JSON 格式返回”写成长期使用的指令，再由程序逐次传入不同文本。使用者每次提交的是待处理材料，具体的处理规则则由应用预先安排。模型看到的输入，因而包括使用者提交的内容，也包括开发者写入的要求。

网页产品已经替用户完成了其中许多安排。对话界面、历史记录、文件上传、搜索和代码执行等能力，通常由产品组合好。用户打开网页就能使用，不必自己处理模型请求、工具调用和结果展示。能够调整哪些指令、接入哪些材料和工具，则取决于产品提供的功能。

通过 API 构建应用时，开发者可以更多地参与这些安排：选择传入什么上下文，编写任务指令，将模型输出交给下一段程序，或者为模型定义可调用的工具。相应地，材料怎样读取、工具怎样执行、结果怎样保存，也需要在应用中接好。

*图 1　网页与 API 应用怎样组织模型输入。点击图片可查看大图。[可编辑源文件](/EconLLM-Lab/diagrams/research-agents/chapter-1/web-and-api.drawio)。*

这解释了为什么使用同一个模型的产品，实际体验可能差别很大。一个侧边栏助手，可以把当前网页内容连同用户的问题交给模型；一个编辑器助手，可以把正在修改的文件和相关代码一起提供给模型。它们所调用的模型可能相同，但模型获得的材料、可使用的工具，以及结果返回的位置，都可以不同。

理解这一点之后，再来看提示词、工作流和智能体之间的演进关系，就容易一些。

## 二、提示词驱动的任务处理

早期使用大语言模型完成任务，主要围绕文本生成展开：给出一段输入，要求模型生成摘要、翻译、解释或代码。用户通过提示词说明任务，模型按照这些要求返回内容。

当一个任务包含多个步骤时，常见的做法是提前写好执行顺序。例如，先要求模型阅读材料，再提取信息，最后按指定格式整理。既可以由用户在网页中逐步提问，也可以通过 API，把几次调用接入一个预设程序。

在这种应用中，提示词承担了很多原本需要写进程序的任务规则。提取哪些内容，先处理什么，遇到不同情况怎样回答，都要提前说明。开发者需要反复调整提示词，让模型的输出能够符合下一步程序的要求。有时，为了完成一个看似简单的任务，提示词反而比待处理材料还长。

任务一旦发生变化，这套安排就需要修改。新增一个字段，要补充定义和示例；改变输出格式，要同时调整提示词与后续处理代码；模型在某类材料上反复出错，还需要继续增加说明。随着例外情况增多，提示词也越来越难维护。

模型本身的能力同样限制了这条路径。写清楚要求，可以减少一部分误解，却不能保证模型能够遵循任意复杂的流程。把更多步骤塞进同一次请求，还会使中间错误更难定位。输出不符合预期时，使用者往往需要重新拆解任务，再决定下一次应该怎样提问。

因此，在这一阶段，任务主要由人提前安排。模型完成其中一次或几次生成，步骤之间如何连接，仍由用户或程序决定。提示词的设计与模型的基准能力，共同影响最终效果。

当任务继续变复杂，仅靠反复改写一段提示词，维护成本就会很高。围绕任务拆分、上下文读取和工具执行，开始出现更多专门的应用。

## 三、工作流与工具集成：Coze、Cursor 与 Manus

这一变化有两方面的推动。

一方面，模型能够处理更长的上下文，也更能完成包含多个步骤的推理任务。材料不必总被切成很短的片段，模型也可以根据已有信息安排部分中间步骤。工具调用能力进一步使模型能够提出具体操作，例如请求搜索、读取文件，或者执行一段程序。

工具调用需要模型与外部程序配合。模型生成调用请求，应用负责执行相应操作，再将结果传回模型。下一次生成便可以利用这些新信息，继续回答或提出新的调用。[OpenAI 官方文档：工具调用流程](https://developers.openai.com/api/docs/guides/function-calling)

另一方面，开发者开始把这些能力组织成更容易使用的工具。对用户来说，通常可以直接调整的是任务怎样拆分、材料怎样进入上下文，以及模型能够调用哪些操作。Coze、Cursor 和 Manus，分别展示了这一过程中的几种思路。

Coze 一类工作流工具，将任务拆成多个节点，再规定节点之间的连接。一个节点负责读取输入，一个节点调用模型提取信息，另一个节点整理输出；需要时，还可以加入条件分支或外部接口。原本挤在一段提示词里的过程，由此可以分开编写和调试。[Coze Studio 官方项目](https://github.com/coze-dev/coze-studio)

这种做法仍然需要人提前设计流程。哪些节点先运行，前一个节点的什么结果交给后一个节点，都要作出安排。遇到新的任务类型，或者原有流程没有覆盖的情况，就需要调整节点和连接。模型承担的工作增多了，流程本身仍主要由开发者规定。

[![扣子官方文档中的文件读取、模型提取与结果整理节点](/EconLLM-Lab/images/research-agents/chapter-1/coze-workflow.webp)](/EconLLM-Lab/images/research-agents/chapter-1/coze-workflow.webp)

*图 3　扣子工作流画布中的文件读取、模型调用与结果整理。来源：[扣子官方文档](https://docs.coze.cn/guides_ai_powered_workflow_development)。*

Cursor、Copilot 这类编辑器中的辅助工具，则直接接入用户正在工作的环境。使用者不必反复复制整段代码，再把模型生成的内容粘贴回来。工具可以读取相关文件，将它们提供给模型，并把修改应用到工作区。Cursor 的 Agent 还可以搜索代码、编辑文件和运行命令。[Cursor 官方文档](https://cursor.com/docs/agent/overview)

这里减少的是上下文搬运和结果转写的负担。模型能够获得当前文件及其相关内容，建议也能够直接落到需要修改的位置。对话与实际操作之间的距离，因而缩短了。

[![Cursor 官方历史界面中同时列出的项目目录和打开的工作区文件](/EconLLM-Lab/images/research-agents/chapter-1/cursor-editor.png)](/EconLLM-Lab/images/research-agents/chapter-1/cursor-editor.png)

Manus 展示了另一种组织方式：为模型准备一套包含浏览器、文件系统和命令行的执行环境，让它根据任务选择工具，连续完成多个步骤。以它的云端沙盒为例，模型可以在分配给任务的计算机环境中读取文件、编写程序和使用浏览器。用户不必为每一个操作单独发出指令。[Manus：云端沙盒的工作方式](https://www.manus.im/blog/manus-sandbox)

*图 5　Manus 的任务执行界面：左侧记录文件、搜索与浏览操作，右侧展示实际网页。来源：[Manus 官方文档](https://manus.im/docs/features/cloud-browser)。*

沿着这些工具的发展，可以看到任务安排正在发生变化。工作流工具帮助人把预设步骤接起来，编辑器集成减少材料与代码的搬运，Agent 则开始根据执行结果，自行决定后续操作。

但执行发生在哪里，仍然影响它能够完成什么。

如果任务运行在独立的云端环境中，而数据、论文目录和常用软件都在自己的电脑上，二者之间仍需要衔接。我们要上传输入文件，下载生成结果，再把结果放回原来的项目。任务完成后，下一次修改还可能需要重新组织这些材料。

以论文写作为例，生成一段大纲或 LaTeX 文本，只涉及内容输出。要继续使用本地已有的文档类、参考文献库和编译配置，就需要进入对应目录，修改文件，调用编译器，再处理编译结果。如果工具没有接入这个环境，这些操作仍要由用户接续。

这就把问题推进了一步：能否让模型直接使用研究者现有的文件和程序，在同一个项目中持续工作？

## 四、模型与本地环境的深度集成

既然模型已经能够拆解部分任务、选择工具，也能够编写代码，那么就可以进一步搭建一个执行框架，把读取文件、编辑内容和运行命令等操作接入其中。模型根据用户目标和当前结果，决定接下来需要读取什么、执行什么，再由框架完成相应操作。

Claude Code 采用的就是这类设计。它在模型周围提供文件和命令工具，并组织模型所需的上下文。模型可以读取项目、修改文件、运行程序，再根据返回的信息继续工作。[Claude Code 官方文档：工作原理](https://code.claude.com/docs/en/how-claude-code-works)

[![独立任务环境与接入本地项目后的执行过程](/EconLLM-Lab/diagrams/research-agents/chapter-1/local-integration.svg)](/EconLLM-Lab/diagrams/research-agents/chapter-1/local-integration.svg)

*图 6　接入已有项目后，文件操作、程序执行与结果反馈可以在同一任务中接续。模型服务仍可位于云端。[可编辑源文件](/EconLLM-Lab/diagrams/research-agents/chapter-1/local-integration.drawio)。*

同样是修改一篇 LaTeX 论文，在已经配置好编译环境的项目中，它可以先查看主文件和相关章节，读取参考文献与格式设置，随后修改对应文件并运行编译。若编译报错，再读取日志，定位问题，继续修改。生成的文件保存在项目目录里，下一次任务可以从这些文件继续。

整理数据也可以采用同样的方式：先读取文件结构，编写处理程序，实际运行，再根据输出检查是否需要调整。模型生成的代码，由执行环境接着运行；运行结果又成为后续判断的输入。

在这样的工作方式下，用户可以交代一项完整任务，让模型在执行过程中安排具体步骤。过去由人反复完成的“读文件、写代码、运行、查看结果、再次修改”，有一部分可以在框架内连续进行。工作流也可以随着实际遇到的文件和错误作出调整。

这里所说的本地集成，指的是模型能够通过工具操作自己的工作区。模型服务仍然可以位于云端，文件读写和程序执行则发生在接入的本地环境中。原来的数据、代码、编译器和其他命令行工具，因而能够进入同一个任务过程。

这也是理解 AI Agent 的一个具体起点：模型获得了可执行的操作，能够利用操作结果继续安排工作。Claude Code 等工具的设计，便围绕怎样提供上下文、怎样让模型使用工具，以及怎样持续推进任务展开。
